02 / 08
-- the bug every dev ships once

If x = NULL
ever bit you —
you're not alone.

SQL doesn't have two truth values. It has three: TRUE / FALSE / NULL.

Most languages treat missing as false or throw. SQL does neither — it returns a third state: UNKNOWN.

That unknown propagates silently. Rows vanish. Counts lie. Joins miss. And nobody tells you why.

04 / 08
-- the classic = NULL trap

= NULL returns
0 rows. Always.

-- bug: never returns anything
SELECT * FROM users
  WHERE deleted_at = NULL;   -- NULL = NULL → NULL, not TRUE

-- fix: use IS NULL
SELECT * FROM users
  WHERE deleted_at IS NULL; -- correct ✓

= NULL is a comparison. It always evaluates to NULL — never TRUE. IS NULL is a predicate specifically for this.

06 / 08
-- COUNT, UNIQUE, JOIN quirks

NULL breaks COUNT.
NULL breaks JOINs.

-- COUNT(col) skips NULLs; COUNT(*) doesn't
SELECT
  COUNT(email)  -- skips rows where email IS NULL
  COUNT(*)      -- counts every row, period
FROM users;

-- JOIN: NULL ≠ NULL — rows won't match
-- use IS NOT DISTINCT FROM for NULL-safe equality
SELECT * FROM a JOIN b
  ON a.code IS NOT DISTINCT FROM b.code;

UNIQUE constraint: PG allows multiple NULLs in a unique column — because NULL ≠ NULL, no violation.

See it yourself.

-- NULL = NULL returns NULL, not TRUE
SELECT NULL = NULL;
-- → ?column? = NULL  (not true!)

-- IS NULL returns TRUE
SELECT NULL IS NULL;
-- → ?column? = t

-- COUNT difference (seed some NULL emails)
SELECT
  COUNT(email)   AS with_email,
  COUNT(*)       AS total_rows
FROM users;
-- with_email < total_rows if any email IS NULL

-- tl;dr

NULL recap

  • NULL = unknown, not zero, not false, not empty string
  • Use IS NULL / IS NOT NULL — never = NULL
  • NULL propagates — one NULL poisons the whole expression
  • COUNT(col) skips NULLs; COUNT(*) counts all rows
  • JOINs won't match NULLs — use IS NOT DISTINCT FROM
  • Use COALESCE(x, default) to substitute a real value
