-- # the argument

Devs argue.
Postgres thrashes.

"No collisions in distributed systems." Sure. But Postgres doesn't care about your philosophy — it cares about where the insert lands in the index.

UUIDv4 is random. Every insert picks a random leaf page in the B-tree.

bigint sequences always append to the rightmost leaf. That's it.

Random vs sequential writes → completely different I/O patterns at scale.

-- # size matters at scale

16 bytes vs 8.
Multiply by millions.

uuid (v4)
16B
per row · every FK reference · every index entry
bigint
8B
per row · half the storage · half the cache pressure
-- verify in psql
SELECT
  pg_column_size(uuid_generate_v4()) AS uuid_bytes,
  pg_column_size(1::bigint)           AS bigint_bytes;

 uuid_bytes │ bigint_bytes
───────────┼─────────────
         16 │ 8

10M rows + 3 FK tables = ~240 MB extra just in UUID overhead.

-- # the fix

UUIDv7 — distributed and
sequential.

Time-ordered UUID. Starts with a millisecond timestamp → inserts cluster at the rightmost leaf, just like bigint.

-- PG 18 native (or use pg_uuidv7 extension)
CREATE EXTENSION pg_uuidv7;

CREATE TABLE orders (
    id   uuid DEFAULT uuidv7() PRIMARY KEY,
  item text
);

-- structure of a UUIDv7:
-- 0192d3a0-4f1e-7... ← timestamp prefix
-- 48-bit ms timestamp | 12-bit seq | random
UUIDv4 — random
→
UUIDv7 — time-ordered
→
same write pattern as bigint

-- # tl;dr

PK choice = write pattern.

  • UUIDv4 random → page splits → cache misses → slow
  • bigint sequential → rightmost leaf → tight, fast
  • size 16B vs 8B — multiplied by every FK and index
  • UUIDv7 time-ordered — distributed IDs, bigint write cost
  • Use UUIDs only when you need distributed uniqueness
