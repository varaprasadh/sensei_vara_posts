$ # the pattern

One query.
Then N more.

# query 1 — fetch all users
users = SELECT * FROM users;

# N queries — one per user
for u in users:
    orders = SELECT * FROM orders
              WHERE user_id = u.id;
⚠ 1 query for users + N queries for orders = N+1 total
N = 100 users → 101 queries fired → 100ms+ latency

$ # fix #1
JOIN — 1 query, all data

DB fetches users and their orders together.
App gets everything in one result set.

SELECT
    u.id,  u.name,  u.email,
    o.id   AS order_id,
    o.total,  o.created_at
FROM   users u
JOIN   orders o  ON  o.user_id = u.id;
1 query total index on orders.user_id hash join in DB

Works best when you always need child rows alongside parent.
Watch out: multiplies rows if user has many orders — handle in app.

$ # fix #2
Batch with IN — 2 queries total

Fetch all users first. Collect their IDs. Fetch all orders in one shot.

# query 1
users = SELECT * FROM users;

# query 2 — collect IDs, one IN clause
ids   = [u.id for u in users]
orders = SELECT * FROM orders
           WHERE user_id IN (1, 2, 3, …);

# group in app: orders_by_user[u.id] = [...]
2 queries, not N+1 → group result in memory

Good when JOIN is awkward (pagination, separate endpoints).
This is exactly what DataLoader does — see next fix.

$ # fix #3 — let the orm do it

Eager loading —
tell the ORM upfront.

Most ORMs hide N+1 by default. They also hide the fix.

Django
User.objects.prefetch_related('orders').all()
Rails / ActiveRecord
User.includes(:orders).all
SQLAlchemy
session.query(User).options(joinedload(User.orders))

All three generate the IN-batch or JOIN internally. One word = fixed.
