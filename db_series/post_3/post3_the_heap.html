-- # insertion order vs heap order

INSERT finds free space.
Not the end.

After deletes, new rows backfill gaps. CTIDs expose the truth.

-- id=1..5 inserted in order, but row 3 was deleted
-- then id=6 inserted — it reused that slot
SELECT ctid, id, name
FROM   users
ORDER BY id;

 ctid  | id |  name
-------+----+--------
 (0,1) |  1 | bob
 (0,2) |  2 | carol
 (0,3) |  6 | zara   -- backfilled slot 3
 (0,4) |  4 | dave
 (1,1) |  5 | eve

id=6 was inserted last yet lives at (0,3). id order ≠ heap order.

-- # the gotcha that bites everyone

No ORDER BY
= no guarantee.

Postgres can return rows in any order it finds efficient. Heap order is not insertion order.

-- This looks fine. It's lying to you.
SELECT * FROM orders;

 id | customer  | amount
----+-----------+--------
  1 | alice     | 120.00
  2 | bob       | 45.00
  3 | carol     | 200.00

-- Works today. Breaks after VACUUM, CLUSTER,
-- parallel scan, or index switch. Random.
Rule: always ORDER BY when order matters.
If you don't say it, Postgres doesn't guarantee it.

-- # see it yourself

Pull heap metadata
from any table.

These columns are always there. Postgres just hides them by default.

SELECT
  ctid,                    -- physical location (page, offset)
  xmin,                    -- tx that created this version
  xmax,                    -- tx that deleted/updated (0 = live)
  *
FROM users
LIMIT 5;

 ctid  | xmin | xmax | id |  name
-------+------+------+----+-------
 (0,1) | 1042 |    0 |  1 | alice
 (0,2) | 1042 |    0 |  2 | bob
 (0,3) | 1043 | 1051 |  3 | carol  -- dead: xmax set
 (0,4) | 1044 |    0 |  4 | dave
 (1,1) | 1045 |    0 |  5 | eve

xmax ≠ 0 = deleted or updated. VACUUM will reclaim it.
