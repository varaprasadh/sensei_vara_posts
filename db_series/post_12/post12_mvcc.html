mvcc.sql 02 / 08
-- the thing most devs assume

UPDATE doesn't
overwrite.

Most devs picture UPDATE as an in-place edit — like changing a cell in Excel. Postgres doesn't do that.

Instead it writes a brand-new row version and marks the old one as dead.

The old row stays on disk — just invisible to new transactions. That's the entire trick.

UPDATE ≠ overwrite
UPDATE = new row version + old marked dead

-- readers never block writers. writers never block readers.

Two sessions.
Zero waiting.

-- Session 1 (xid=300): heavy writer
UPDATE orders SET status = 'shipped'
WHERE id BETWEEN 1 AND 100000;
-- updating 100k rows…

-- Session 2 (xid=301): concurrent reader
SELECT count(*) FROM orders;  -- no lock. returns instantly.
-- sees snapshot from before session 1 started
-- no waiting, no blocking
readers
see consistent snapshot
⟂
writers
write new versions

They operate on different versions of the same data. No coordination needed.

See xmin, xmax
with your own eyes.

-- check your current transaction id
SELECT txid_current();
-- → 4019

-- inspect tuple headers directly
SELECT xmin, xmax, id, name FROM users WHERE id = 1;
-- xmin | xmax | id | name
-- -----+------+----+-------
--  100 |    0 |  1 | Alice   ← xmax=0 means ∞ (alive)

-- now update it
UPDATE users SET name = 'Bob' WHERE id = 1;

-- re-check — new xmin, old row vanished from SELECT
SELECT xmin, xmax, id, name FROM users WHERE id = 1;
-- xmin | xmax | id | name
-- -----+------+----+-----
--  4019|    0 |  1 | Bob     ← new tuple, born in txid 4019

The old tuple (xmax=4019) is still on the page — invisible to you, visible to VACUUM.

-- recap

MVCC in five lines.

  • UPDATE = new row version + old marked dead (xmax set)
  • Each txn takes a snapshot — sees only rows committed before it started
  • Readers never block writers; writers never block readers
  • Dead tuples accumulate → table bloat
  • VACUUM reclaims dead space, keeps pages lean
