-- # the uncomfortable truth

SELECT is first.
It runs second-to-last.

You write SELECT at the top of every query. The engine evaluates it near the bottom. That one fact explains 80% of SQL surprises.

You write
SELECT
FROM
WHERE
GROUP BY
HAVING
ORDER BY
LIMIT
≠
Engine runs
FROM
WHERE
GROUP BY
HAVING
SELECT
ORDER BY
LIMIT

-- # two orders, side by side

Written order vs Execution order

Written order
  • 1SELECTwhat to return
  • 2FROMwhich table(s)
  • 3WHERErow filter
  • 4GROUP BYaggregate
  • 5HAVINGgroup filter
  • 6ORDER BYsort
  • 7LIMITcut rows
Execution order
  • 1FROMload rows + joins
  • 2WHEREfilter raw rows
  • 3GROUP BYform groups
  • 4HAVINGfilter groups
  • 5SELECT⟵ happens here!
  • 6ORDER BYsort results
  • 7LIMITtrim output

-- # the classic bug

Alias in WHERE? Error.

SELECT hasn't run yet. Aliases don't exist at WHERE time.

-- ❌ BROKEN: alias 't' used before it exists
SELECT email, total AS t
FROM   orders
WHERE  t > 100;
-- ERROR: column "t" does not exist
fixes
Option 1 — original column
SELECT email, total AS t
FROM   orders
WHERE  total > 100;
Option 2 — CTE
WITH base AS (
  SELECT email, total AS t
  FROM orders
)
SELECT * FROM base WHERE t > 100;

-- # most confused pair in SQL

WHERE ≠ HAVING

WHERE — filters rows
SELECT user_id, COUNT(*)
FROM   orders
WHERE  status = 'paid'
GROUP BY user_id;
Runs before GROUP BY.
Filters individual rows.
Cannot use aggregates.
HAVING — filters groups
SELECT user_id, COUNT(*) AS n
FROM   orders
GROUP BY user_id
HAVING COUNT(*) > 5;
Runs after GROUP BY.
Filters whole groups.
Can use aggregates.

-- # all clauses, one query

Every clause. Annotated.

Paste this. Mentally trace the execution order.

SELECT   user_id, COUNT(*) AS c  -- ⑤ select: alias 'c' born here
FROM     orders                   -- ① load rows first
WHERE    total > 0               -- ② filter rows (no aliases!)
GROUP BY user_id                  -- ③ collapse into groups
HAVING   COUNT(*) > 5           -- ④ filter groups (agg ok)
ORDER BY c DESC                  -- ⑥ 'c' visible here ✓
LIMIT    10;                      -- ⑦ trim output last
Why this fails
WHERE c > 5  -- ❌ 'c' not born yet
Why this works
ORDER BY c -- ✓ SELECT already ran

-- # tl;dr

Quick recap

  • Execution: FROM→WHERE→GROUP→HAVING→SELECT→ORDER→LIMIT
  • SELECT aliases visible in ORDER BY only — not WHERE/HAVING
  • WHERE filters rows (pre-aggregation)
  • HAVING filters groups (post-aggregation)
  • Confused? Wrap in a CTE — makes order explicit
