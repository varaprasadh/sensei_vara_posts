-- # what you wrote vs what pg ran

You wrote JOIN.
Postgres ran a loop.

Which loop? Depends on your data. Three choices. One planner decision.

nested loop
|
hash join
|
merge join

Slow join? The fix depends on which loop ran.
EXPLAIN shows you. Most devs never look. 

EXPLAIN SELECT * FROM users u
JOIN orders o ON o.user_id = u.id;
-- → Hash Join  (cost=245.00..890.50 rows=5000)
--     →  Seq Scan on orders
--     →  Hash on users

-- # strategy 1 of 3

Nested Loop
for each row in A, scan B

-- pseudocode
for row_a in table_A:
  for row_b in table_B:
    if row_a.id == row_b.fk:
      emit(row_a, row_b)

-- with index on B:
for row_a in table_A:
    index_lookup(B, row_a.id)
  emit match

-- O(n) not O(n²)

  • Planner picks 1 of 3: nested loop / hash / merge
  • NL — needs small outer or index on inner
  • Hash — needs work_mem, equality only
  • Merge — needs sort, no extra memory
