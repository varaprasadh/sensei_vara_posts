Most devs use B-tree everywhere. For arrays, jsonb, huge time-series tables — it does nothing. You burn disk and get no speedup.

B-tree — sorted.
Equality + range + sort.

WHERE age = 30                        -- equality ✓
WHERE age BETWEEN 20 AND 40           -- range   ✓
ORDER BY age                           -- sort    ✓

-- # gin index

GIN — generalized inverted.
Arrays · JSONB · full-text.

WHERE tags @> ARRAY['db', 'postgres']    -- array overlap ✓
WHERE doc @@ to_tsquery('postgres')    -- full-text   ✓
WHERE data @> '{"role":"admin"}'::jsonb  -- jsonb       ✓

-- # pick by query shape

Decision matrix

Type Use when Size Example query
B-tree equality, range, sort — anything ordered medium WHERE age BETWEEN 20 AND 40
Hash equality only, high-cardinality exact match small WHERE email = 'x@x.com'
GIN arrays, jsonb, tsvector — "contains X" large WHERE tags @> '{db}'
BRIN huge table, data naturally ordered by col tiny WHERE created_at > '2026-01-01'

Wrong type → index exists but planner ignores it.
No speedup. Just wasted disk.

-- # tl;dr

Quick recap

  • B-tree — default. equality + range + sort. Almost always right.
  • Hash — equality only, niche. Slightly smaller than B-tree.
  • GIN — arrays / jsonb / full-text. "Does row contain X?"
  • BRIN — huge append-only tables, physically ordered. Tiny index.
  • Pick by query shape, not habit.
