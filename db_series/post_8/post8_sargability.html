where.sql 01 / 08
# HOOK

You added the index.
Query is still slow.

Most devs check: "Is there an index?" ✓
Few check: "Can the index actually be used?"

An index only works if Postgres can binary-search it.
Wrap the column in a function — the sorted structure becomes useless.

-- You think this uses the index on email:
SELECT * FROM users
WHERE lower(email) = 'alice@x.com';

-- PG sees: compute lower() for EVERY row → Seq Scan

The problem has a name: sargability (Search-ARGument-able).

# SARGABLE vs NOT
✗ NOT SARGABLE
SELECT * FROM users
WHERE lower(email)
    = 'a@x.com';
✓ SARGABLE
SELECT * FROM users
WHERE email
    = 'a@x.com';
EXPLAIN output
Seq Scan on users
  Filter: lower(email::text)
          = 'a@x.com'
  Rows Removed: 999999
  cost=0.00..22483.00
EXPLAIN output
Index Scan using
  users_email_idx
  on users
  Index Cond: email = 'a@x.com'
  cost=0.42..8.44

# WHY THE INDEX CAN'T HELP

B-tree is sorted by the stored value. Applying lower() asks for a value that was never indexed.

killers.sql 04 / 08
# OTHER INDEX KILLERS

Any expression that wraps the column breaks sargability:

  • WHERE email || '' = 'a@x.com' → useless concat forces full scan
    Seq Scan
  • WHERE date_trunc('day', created_at) = '2024-01-01' → use range: created_at >= '2024-01-01' AND < '2024-01-02'
    Seq Scan
  • WHERE id::text = '42' → cast the constant: WHERE id = 42
    Seq Scan
  • WHERE col + 1 > 10 → move op to constant side: WHERE col > 9
    Seq Scan

Rule: column alone on one side, expression on the other.

functional_index.sql 05 / 08
# THREE FIXES
FIX 1 — normalize at write time
-- store already-lowercased
ALTER TABLE users ADD COLUMN
  email_lc text GENERATED ALWAYS AS
  (lower(email)) STORED;
CREATE INDEX ON users(email_lc);
-- now: WHERE email_lc = 'a@x.com'  ← sargable
FIX 2 — functional index (no schema change)
-- index the expression itself
CREATE INDEX users_email_lower_idx
  ON users(lower(email));

-- Postgres matches the expr in WHERE:
SELECT * FROM users
WHERE lower(email) = 'a@x.com';
-- ↑ now uses the functional index ✓

recap.sql 07 / 08
# RECAP
  • function on column → index can't binary-search → Seq Scan
  • sargable = column bare on predicate side
  • move operations to the constant side (col > 9 not col+1 > 10)
  • functional index: index the expression, not just the column
  • or normalize on write — store the transformed value
