-- # the myth

"FKs are slow.
Drop them at scale."

'FKs are slow' is the dev folklore that's cost more data integrity than any bug.

The "scale" argument: an extra index lookup on INSERT/UPDATE/DELETE. Cost: microseconds.

What you pay instead: orphan rows. Phantom order IDs. Users that don't exist. Silent corruption — no crash, no error, just wrong data.

An FK is a DB-enforced contract: this value MUST exist in that other table.

04 / 08
-- # declaring the constraint

FK syntax + ON DELETE options

CREATE TABLE orders (
  id       BIGINT    PRIMARY KEY,
  user_id  BIGINT    NOT NULL,  -- the FK column
  CONSTRAINT fk_orders_user
    FOREIGN KEY (user_id)
    REFERENCES users(id)
    ON DELETE CASCADE          -- <-- action
);
CASCADE · SET NULL · RESTRICT · NO ACTION
CASCADE delete parent → delete children
SET NULL delete parent → null the FK
RESTRICT block delete if children exist
NO ACTION like RESTRICT, deferred check

-- # the real performance story

The cost is tiny.
The risk is not.

What an FK actually does on INSERT:

COST
1 index lookup on
users(id)
~1–10 µs
B-tree lookup, likely in pg_buffer_cache
WITHOUT FK
Bad writes succeed
silently at full speed
∞ tech debt
corruption found in prod, not tests

The FK index is almost always hot in cache. The lookup is free in practice. You're paying nothing.

-- # cascade in action

One DELETE.
DB cleans up automatically.

-- user 5 closes their account
DELETE FROM users WHERE id = 5;

-- CASCADE: all orders.user_id=5 also deleted
-- no orphan rows. DB handles it.

-- WITHOUT FK: you'd write this manually...
DELETE FROM orders  WHERE user_id = 5;
DELETE FROM reviews WHERE user_id = 5;
DELETE FROM sessions WHERE user_id = 5;
-- ...and forget one. Orphans accumulate.

-- # inspect your FKs right now

See it in psql.

-- describe the table (shows FK constraints)
\d orders

Foreign-key constraints:
  "fk_orders_user" FOREIGN KEY (user_id)
    REFERENCES users(id) ON DELETE CASCADE

-- query pg_constraint directly
SELECT
  conname   AS constraint_name,
  contype   AS type       -- 'f' = foreign key
FROM  pg_constraint
WHERE conrelid = 'orders'::regclass;

-- # tl;dr

Quick recap

  • FK = "this value MUST exist in that other table"
  • DB enforces on INSERT / UPDATE / DELETE
  • ON DELETE options: CASCADE · SET NULL · RESTRICT
  • Cost = 1 index lookup ≈ ~µs. Almost free.
  • Without FK: orphan rows accumulate silently
  • Always declare FKs. Drop them only with a real benchmark.
