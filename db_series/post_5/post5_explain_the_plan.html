02 / 08
-- your sql is a request, not instructions

You write intent.
Postgres decides how.

You write SELECT … WHERE id = 42. The query planner rewrites that into an execution plan — an operator tree with joins, scans, sorts.

The SQL string is irrelevant to performance.
The plan is what runs.

your SQL
→ planner →
execution plan
→ executor →
rows

Two different SQLs can produce identical plans. Same SQL on different data → different plans. Read THAT.

03 / 08
-- seq scan vs index scan

Same query.
Two different plans.

-- no index on email
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';

Seq Scan on users  (cost=0.00..241.00 rows=1 width=64)
  Filter: (email = 'alice@example.com')

-- after: CREATE INDEX ON users(email)
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';

Index Scan using users_email_idx  (cost=0.42..8.44 rows=1 width=64)
  Index Cond: (email = 'alice@example.com')

Seq Scan = read every row. Index Scan = jump straight to matching rows. Cost drops from 241 → 8.44.

05 / 08
-- decode the cost string

What the numbers
actually mean.

Index Scan  (cost=0.42..8.44  rows=1  width=64)
cost=0.42..
startup cost
cost before first row emitted — index traversal, hash build, sort
..8.44
total cost
cost to emit all rows — what matters for most queries
rows=
est. rows
planner's guess based on table statistics, not a measurement
width=
avg bytes
average row width in bytes — affects sort & hash memory

Cost units are arbitrary. Compare plans relative to each other, not absolute numbers. These are estimates, not measurements.

06 / 08
-- estimates vs actuals

ANALYZE adds
real numbers.

EXPLAIN ANALYZE
  SELECT * FROM users WHERE id = 42;

Index Scan using users_pkey on users
  (cost=0.42..8.44 rows=1 width=64)
  (actual time=0.012..0.014 rows=1 loops=1)
  Index Cond: (id = 42)
Planning Time: 0.184 ms
Execution Time: 0.041 ms

Highlighted line = actual measurements. Compare to cost estimates above it.

rows estimate = 1. actual rows = 1. Planner was right.
When they diverge badly → stale stats. Run ANALYZE tablename.

Full EXPLAIN.
Run this now.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
  SELECT o.id, u.email, o.total
  FROM orders o
  JOIN users u ON u.id = o.user_id
  WHERE o.status = 'pending';

Hash Join  (cost=42.0..580.0 rows=240 width=48)
           (actual time=1.2..14.7 rows=237 loops=1)
  Buffers: shared hit=82 read=144   ← 144 disk reads!
  ->  Seq Scan on orders  (actual time=0.03..9.1 rows=10000)
        Filter: (status = 'pending')
        Rows Removed by Filter: 9763   ← index opportunity
  ->  Hash  (actual time=0.8..0.8 rows=500)
        Buckets: 1024  Batches: 1  Mem: 42kB
        ->  Index Scan using users_pkey ...

BUFFERS shows disk vs cache hits. 144 reads + 9763 rows filtered = add an index on orders(status).
