Most devs don't know what it actually allows.

 read committed     ← PG default

Each statement gets a fresh snapshot. Two reads in the same transaction can see different data.

That's not a bug. That's the contract.

-- strongest isolation

Serializable —
as if one at a time

PG uses SSI (Serializable Snapshot Isolation). No locks — but it watches for conflicts. If it detects a cycle, it aborts one txn.

-- PG detects the conflict and aborts
ERROR:  could not serialize access due to concurrent update
-- DETAIL:  Process 1234 updated rows then Process 5678 read them.
-- You must ROLLBACK and retry the transaction.
when to use
financial logic, seat reservation, any "check then insert" pattern
cost
higher contention → more aborts. You must retry on serialization failure.

See it yourself

-- check your default
SHOW transaction_isolation;
--  read committed

-- open two sessions. session 1:
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM accounts WHERE id = 1; -- note the value

-- session 2: UPDATE accounts SET balance=999 WHERE id=1; COMMIT;

-- back in session 1 — same txn:
SELECT * FROM accounts WHERE id = 1;
-- still sees original value  ← snapshot pinned!
COMMIT;

Repeatable Read: snapshot locked at first statement in txn, not at BEGIN.

Recap

  • Read Committed — default · statement-level snapshot
  • Repeatable Read — txn-level snapshot · no phantom in PG
  • Serializable — strongest · SSI · may abort → retry
  • No dirty reads in PG at any level
  • Pick per workload — don't default everywhere to Serializable
