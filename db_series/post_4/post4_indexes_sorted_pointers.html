-- most devs treat this as a black box

Indexes feel
magic.
They're not.

Add an index, query goes from 800ms → 2ms. Feels like sorcery.

But there's no magic. Under the hood it's a sorted data structure — a B-tree — that stores (key, ctid) pairs and lets Postgres skip scanning every row.

ctid = physical location of the row on disk. The index just says: "this key lives here."

key value → ctid (page, offset) → heap row

05 / 08
-- the proof is in EXPLAIN

Before vs after
one line.

-- create the index
CREATE INDEX idx_users_email ON users(email);

-- same query. wildly different plans.
EXPLAIN SELECT * FROM users WHERE email = 'alice@x.com';
BEFORE (no index)
Seq Scan on users
  (cost=0.00..18400.00
   rows=1 width=64)
  Filter: (email =
    'alice@x.com')
AFTER (with index)
Index Scan using
  idx_users_email
  (cost=0.43..8.45
   rows=1 width=64)
  Index Cond: (email =
    'alice@x.com')

Cost dropped from 18400 to 8.45. Postgres didn't read every row — it descended the B-tree.

06 / 08
-- nothing is free

Faster reads.
Real costs.

An index isn't just a win. Every index you add is a contract — reads get cheaper, everything else gets slightly more expensive.

reads ↑
Faster SELECTs
Binary search through B-tree instead of full table scan. Millions of rows → same log(n) hops.
writes ↓
Slower writes
Every INSERT / UPDATE / DELETE must also update the B-tree. More indexes = more overhead per write.
disk ↑
More disk
Index lives in a separate file. A wide table with 10 indexes can double its disk footprint.

Rule of thumb: index columns you filter, join, or sort on. Not everything.

-- tl;dr

Quick recap

  • index = sorted (key, ctid) pairs — not row data
  • lives in a separate file from the heap
  • B-tree default — descent is O(log n)
  • makes reads fast, makes writes slower
  • not free — costs disk space + write overhead
