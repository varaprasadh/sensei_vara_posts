psql=# what most devs get wrong

DB isn't a
black box.
It's a directory.

Most devs treat Postgres like a network oracle — send SQL, receive rows. Totally wrong frame.

At its core, Postgres is a process that reads and writes files on disk.

Tables → files. Indexes → files. Schema → files. WAL → files.

That directory is $PGDATA. Everything lives there.

04 / 08
psql=# a table is literally a file

Table name → oid → filename.

Postgres assigns every relation an object ID. That OID is the filename in base/.

-- find the file on disk for 'users' table
SELECT pg_relation_filepath('users');

-- result:
 pg_relation_filepath
──────────────────────
 base/16384/16421
users → oid 16421 → base/16384/16421

That file grows as rows are inserted. Segment caps at 1GB → gets a sibling: 16421.1, 16421.2…

06 / 08
psql=# what SQL actually does at the OS level

INSERT = append bytes.
SELECT = read bytes.

Every SQL statement bottoms out at a file operation. That's it.

-- this SQL…
INSERT INTO users (name, email)
  VALUES ('alice', 'alice@ex.com');

-- …does this at the OS level:
pwrite(fd, tuple_bytes, len, page_offset)
-- writes serialized tuple into current page
-- then logs it to pg_wal/ for durability

SELECT → pread() pages into memory, scan tuples, return matching rows. No magic.

-- 1. find your data directory
SHOW data_directory;
-- /var/lib/postgresql/16/main

-- 2. list DB dirs on disk
$ ls $PGDATA/base/
-- 1  16384  pgsql_tmp ...

-- 3. find your table's file

-- base/16384/16421

-- 4. check file size vs pg_relation_size
SELECT pg_size_pretty(pg_relation_size('users'));
$ ls -lh $PGDATA/base/16384/16421   # same number

psql=# tl;dr

Quick recap

  • $PGDATA — one directory, all of Postgres lives here
  • base/ — every table & index is a file named by OID
  • pg_wal/ — write-ahead log for durability
  • file → 8KB pages → tuples — that's the stack
  • SELECT reads pages; INSERT appends bytes — no black box
