// index-only scan: name your columns

Index can't satisfy * — heap fetch required.

-- BAD: forces heap fetch
EXPLAIN SELECT * FROM users WHERE id = 42;

  Index Scan on users
    Index Cond: (id = 42)
    Heap Fetches: 1                      ← hits the heap
-- GOOD: index covers (id, email) → index-only
EXPLAIN SELECT id, email FROM users WHERE id = 42;

  Index Only Scan on users
    Index Cond: (id = 42)
    Heap Fetches: 0                      ← never touches heap

Index CREATE INDEX ON users(id) INCLUDE (email) makes this possible. SELECT * kills it.

// TOAST — the hidden sidecar

TOAST: big columns live in a side table.

Column > ~2 KB → Postgres offloads it. Inline row stores a pointer. SELECT * dereferences every pointer.

Name your columns → TOAST pointers for unused fields never dereferenced.

Run this. Watch Heap Fetches drop.

-- needs: CREATE INDEX ON users(id) INCLUDE (email);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id = 1;

  →  Heap Fetches: 1   Buffers: shared hit=4
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, email FROM users WHERE id = 1;

  →  Heap Fetches: 0   Buffers: shared hit=2

Heap Fetches: 0 = pure index read. Buffers halved. No heap I/O. Scales to millions of rows.

Name your columns. Always.

  • SELECT * ships every byte — even bytes you discard
  • index-only scan needs a covering index — * kills it
  • TOAST = hidden cost — big cols live off-heap, * dereferences all
  • wide rows hurt cache locality — fewer rows fit per page
  • SELECT * OK only in psql exploration — never in app code
