-- # the trap most devs fall into

Postgres has the best
JSONB in any RDBMS.

That doesn't mean you should put everything in it.

the trap
Best tool for X → use it for everything
Every column becomes a JSONB key
the truth
JSONB shines at genuine uncertainty
Known fields → real columns, always

The feature is powerful. The misuse is common. Know the difference.

-- # what JSONB actually is

Binary-encoded JSON.
Indexable. Queryable.

-- store arbitrary JSON
INSERT INTO events(payload)
VALUES ('{"type":"click","x":12}'::jsonb);

-- path access operators
SELECT payload->>'type'  -- text: "click"
FROM   events;

-- nested path
SELECT payload->'user'->>'email' FROM events;
->get as jsonb
->>get as text
@>contains
?key exists
#>>path as text

-- # the GIN index — why JSONB is fast

GIN turns containment
into an index scan.

-- one line to index the whole column
CREATE INDEX ON events USING GIN (payload);

-- now this uses the index instead of seqscan
SELECT * FROM events
WHERE  payload @> '{"type":"click"}';

-- path_ops variant — smaller, faster for @> only
CREATE INDEX ON events
  USING GIN (payload jsonb_path_ops);
GIN default
supports @>, ?, ?|, ?&
jsonb_path_ops
@> only — 2–4× smaller

-- # when JSONB is the right call

Use it for genuine
schemalessness.

✓
Audit / event payloads Shape varies per event type. You append, rarely filter.
✓
Sparse user-defined fields SaaS custom attributes — different keys per tenant, mostly absent.
✓
External API responses Third-party payloads you need verbatim. Schema is theirs, not yours.

06 / 08
-- # when JSONB punishes you

The wrong tool creates
the wrong pain.

✗
Filtering on it constantly → make it a column
✗
Need FK into it → impossible. Can't reference a JSON key.
✗
JSONB as your whole schema → debugging nightmare 
-- antipattern: everything in JSONB
SELECT data->>'user_id', data->>'email'
FROM   users WHERE data->>'status' = 'active';
-- no types, no FK, no index on status

-- # try it yourself

Copy-paste into psql.

-- query nested path + containment filter
SELECT payload->'user'->>'email'
FROM   events
WHERE  payload @> '{"action":"signup"}';

-- add the GIN index to make it fast
CREATE INDEX idx_events_payload
  ON events USING GIN (payload jsonb_path_ops);

-- verify it hits the index
EXPLAIN ANALYZE
  SELECT * FROM events
  WHERE payload @> '{"action":"signup"}';
sample output
alice@example.com
bob@example.com
(2 rows) — Bitmap Index Scan on idx_events_payload

-- # tl;dr

Quick recap

  • JSONB — binary-encoded JSON, stored decomposed
  • GIN — enables containment & key-existence index scans
  • Use for genuine schemalessness — events, sparse attrs, external payloads
  • Queried/filtered constantly → promote to a column
  • No FKs into JSONB — referential integrity impossible
