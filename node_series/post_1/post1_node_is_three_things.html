$ # layer 1 — the JS engine

V8

Google's C++ engine. Parses, compiles, and runs your JS. Has nothing to do with I/O.

Ignition
Bytecode interpreter. Fast startup.
TurboFan
JIT compiler. Hot code → machine code.
GC
Orinoco GC. Manages your JS heap.
JS Heap
Where objects live. ~1.5GB default.

$ # layer 2 — the C library nobody mentions

libuv

The reason Node is "async". Pure C. Gives Node the event loop, thread pool, and OS-level I/O.

Event Loop
6 phases. Drives the whole async model.
Thread Pool
4 threads (default). Handles blocking ops: fs, dns, crypto.

Bindings

Every core module — fs, http, crypto — is a thin JS wrapper around a C++ binding that calls into libuv or the OS.

// peek at what's beneath require('fs')
const binding = process.binding('fs');
// → C++ FSReqCallback, binding.open, etc.

// or inspect the internal loader:
require('module')._resolveFilename('fs');
// → 'fs'  (built-in, no file path — it's native)

Nothing here is pure JS magic. It's all C underneath.

$ # see the three layers yourself

One command.
All versions.

Drop this in any Node REPL. See all three components at once.

// in any Node REPL or script
console.log(process.versions);

// output:
{
  node:    '22.4.0',       // Node runtime itself
  v8:      '13.2.152.21',  // V8 engine — your JS runs here
  uv:      '1.48.0',       // libuv — event loop lives here
  openssl: '3.0.13',       // crypto bindings
  zlib:    '1.3.0.1',
  modules: '127'           // ABI version for native addons
}

v8 and uv are first-class citizens. They're in process.versions because Node considers them part of itself.

Quick recap

  • Node = V8 + libuv + bindings — not a language
  • V8 executes JS, JIT-compiles, manages GC
  • libuv = event loop + thread pool + async I/O
  • bindings = JS↔C glue — every core module uses them
  • Nothing here is JS-only magic. It's all C underneath.
