rejection.js 03 / 08
⚠ the fire-and-forget trap

Nobody home
to catch it.

// async callback inside setInterval
setInterval(async () => {
  await maybeFail();   // ← rejects, nobody catches
}, 1000);

// maybeFail() rejects on tick #3...
// process.on('unhandledRejection') fires
// Node 15+: EXIT CODE 1. Server gone.

The setInterval callback is just a fn. The returned Promise floats into the void. No outer .catch = no one listening.

process.on.js 04 / 08
✓ three patterns to fix it
A — try/catch inside async fn
setInterval(async () => {
  try { await maybeFail(); }
  catch (err) { log(err); }
}, 1000);
B — .catch on the returned promise
setInterval(() => {
  maybeFail().catch(err => log(err));
}, 1000);
C — global handler (last resort)
process.on('unhandledRejection', (err) => {
  log(err); // still crashes by default
});

A or B = preferred. C = safety net, not a strategy.

⚠ fire-and-forget in route handlers

Orphaned rejection
kills the server.

// ❌ doStuff() is async — rejection orphaned
app.get('/x', (req, res) => {
  doStuff();          // ← promise returned, ignored
  res.send('ok');
});

// ✓ fix A: await it (make handler async)
app.get('/x', async (req, res) => {
  await doStuff();    // ← caught by express-async-errors
  res.send('ok');
});

// ✓ fix B: attach .catch explicitly
doStuff().catch(next);

$ see it yourself
// trigger unhandled rejection → crash
async function boom() {
  throw new Error('unhandled!');
}
boom();  // no await, no .catch
// exit code: 1 ↑ Node 15+
// add global handler → graceful shutdown
process.on('unhandledRejection', (err, promise) => {
  console.error('caught:', err.message);
  // log, alert, then exit cleanly
  process.exit(1);
});
boom();
// → "caught: unhandled!" then exits 1

Global handler = observe & log. Still exit — dirty state is dangerous.
