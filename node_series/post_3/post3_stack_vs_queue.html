$ # step by step: why A C B?

Walk the runtime.

console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
EXECUTION ORDER
1. log('A') → pushed → prints A → popped
2. setTimeout → pushed → hands cb to libuv → popped
3. log('C') → pushed → prints C → popped
4. stack empty → loop checks queue
5. cb (log 'B') → pulled from queue → pushed → prints B
OUTPUT
A
C
B
B runs after current stack clears —
even with 0ms delay.

$ # async = handoff, not halt

fs.readFile() returns immediately.

JS hands path + callback to libuv. Immediately returns. libuv worker reads disk. When done: enqueues callback. Loop delivers it when stack is clear.

$ # the antipattern that jams everything

Blocking = stack never empties.

const end = Date.now() + 5000;

while (Date.now() < end) {} // busy-loop 5s

// nothing else can run during this time:
// no timers fire, no I/O callbacks, no UI
console.log('finally...'); // only runs after 5s
stack jammed for 5s → queue starved → server frozen

The event loop can only pull callbacks when the stack is empty. Block the stack = block everything. In Node: one blocked request blocks all requests.

Prove it yourself.

const t0 = Date.now();
const ts = () => String(Date.now() - t0).padStart(4)+'ms';

console.log(ts(), '[sync] before setTimeout');

setTimeout(() => {
  console.log(ts(), '[cb]   timer fired');
}, 100);

console.log(ts(), '[sync] after setTimeout');
console.log(ts(), '[sync] continuing sync work...');
$ node see_it.js
0ms [sync] before setTimeout
1ms [sync] after setTimeout ← JS didn't wait
1ms [sync] continuing sync work...
101ms [cb] timer fired ← callback finally runs

Quick recap

  • one stack, one thread — always
  • async = handoff to libuv, not pause
  • queue feeds stack when empty (via event loop)
  • blocking = stack jammed = nothing else runs
  • libuv runs the parallel parts (thread pool)
