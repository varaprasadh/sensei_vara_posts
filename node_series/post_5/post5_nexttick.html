$ # Node uses this internally

Why Node uses
nextTick internally.

EventEmitter emits errors via nextTick so your code has time to attach a .on('error') handler first.

// simplified EventEmitter internals
function emitError(emitter, err) {
  process.nextTick(() => {
    emitter.emit('error', err);  // deferred!
  });
}

// your code — listener attaches synchronously
const stream = createStream();
stream.on('error', handler);  // ← runs FIRST
// nextTick fires after — error is caught ✓

Without nextTick: error emits before listener attaches → uncaught exception.

$ # the footgun — recursive nextTick

Recursive nextTick
starves everything.

function loop() {
  process.nextTick(loop);  // ← schedules itself again
}
loop();

// this NEVER runs:
setTimeout(() => console.log('timer'), 0);
// I/O callbacks? Also never.
I/O never fires. Timers never fire.
nextTick queue drains before the loop advances.
Recursive → infinite drain → event loop blocked forever.

Fix: use setImmediate — runs after current I/O, yields to the loop.

See it
yourself.

let i = 0;

// setTimeout(0) — should fire "immediately"
setTimeout(() => console.log('⏱ timer fired'), 0);

// recursive nextTick — starves the timer
function spin() {
  if (i++ < 5) {
    console.log('nextTick #' + i);
    process.nextTick(spin);  // starvation!
  }
}
spin();

// fix: swap nextTick ↑ with setImmediate(spin)
// timer fires between iterations

Run as-is: timer prints last. Swap to setImmediate: timer fires after first spin.

Quick recap

  • nextTick = highest priority queue in Node
  • runs before microtasks (Promises) and macrotasks
  • use for "defer to after current op, before anything else"
  • recursive nextTick = event loop starvation — I/O dies
  • prefer setImmediate for recursion — yields to the loop
