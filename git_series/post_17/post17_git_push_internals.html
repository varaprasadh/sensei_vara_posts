$ # how we think about it

"Send my commits" —
feels simple.

Run git push, see the green progress bar, done. But there are actually 4 distinct phases happening.

$ git push
Enumerating objects: 12, done.
Counting objects: 100% (12/12), done.
Compressing objects: 100% (8/8), done.
Writing objects: 100% (9/9), 1.2 KiB | 1.2 MiB/s, done.
Total 9 (delta 3), reused 0 (delta 0)
remote: ...
To github.com:org/repo.git
   e89df01..d4a1cc7  main -> main

That output? It's 4 phases. Let's break them down.

$ # step 1

Open a channel.

Git opens a transport (SSH, HTTPS, or git://) to the remote. Authenticates. Exchanges capabilities.

• Auth (SSH key or token)
• Negotiate protocol version
• Exchange supported features (multi-ack, sideband, ...)

Everything else happens over this channel.

04 / 08
$ # step 2

What does the remote have?

Both sides exchange ref tips. Your client figures out which commits the remote is missing.

# remote's tips:
main      → e89df01
develop   → b72cf81

# your tips:
main      → d4a1cc7   (3 commits ahead)

# need to send: c91e3b4, f12a08d, d4a1cc7

No wasted bandwidth — only what they're missing.

Pack it into a packfile.

All the commits, trees, and blobs the remote needs get bundled into one delta-compressed file.

objects to send:
- 3 commits
- 5 trees
- 4 blobs
        ↓ delta compression
packfile: 1.2 KiB

Same packfile format git uses on disk (see next post).

update.git
06 / 08
$ # step 4

Send. Update refs.

The remote receives the packfile, runs pre-receive hooks, atomically updates its ref pointers, then runs post-receive hooks.

# remote-side:
1. Receive packfile
2. Verify objects, unpack
3. Run pre-receive hook    (CI gates, branch protection)
4. Update refs/heads/main → d4a1cc7
5. Run post-receive hook   (deploy, notify Slack)

Branch protection and CI gates? They live in step 4.

$ # the most common error

Why pushes get rejected.

If the remote ref isn't an ancestor of your commit, git refuses. Otherwise you'd erase commits.

$ git push
 ! [rejected]        main -> main (non-fast-forward)
hint: Updates were rejected because the tip of your current
hint: branch is behind its remote counterpart.

Fix: git pull --rebase then push. Or if you rewrote history intentionally — --force-with-lease (see post 14).

Quick recap

  • git push = 4 steps: handshake → negotiate → packfile → update
  • only the missing commits get sent
  • server-side hooks run on every push (branch protection, CI)
  • non-fast-forward error = remote has commits you don't
  • --force-with-lease for intentional rewrites only
