$ # the actual commands

Start. Bad. Good. Test.

Tell git the boundaries. Git picks the midpoints for you.

$ git bisect start
$ git bisect bad                  # current commit is broken
$ git bisect good v1.0            # this tag was working

# git checks out a midpoint commit
# you run your test...
$ git bisect good                 # or `bisect bad`

# repeat. git narrows it down each step.

$ git bisect reset                # clean up when done

Tell git the boundaries. It does the rest.

bisect run — fully automatic.

Give it a script that exits 0 (good) or non-0 (bad). Walk away.

$ git bisect start HEAD v1.0
$ git bisect run npm test
# git checks out commits, runs `npm test`,
# and reports the first bad commit when done

a3f8e90 is the first bad commit
commit a3f8e90
Author: alice
Date:   2026-04-12
    refactor session handling

Even a flaky test? bisect skip marks "can't tell" and moves on.

Best when...

Bisect works on any history, but it shines when these line up.

01
linear history
Merges + branches still work, but linear is fastest.
02
deterministic test
Pass / fail must be reproducible. No flakes.
03
fast test loop
You'll run it ~log₂(n) times. Seconds > minutes.
04
clear good baseline
A known-working tag or commit to anchor on.

$ # don't forget the reset

Bisect leaves you
in a detached state.

When bisect ends, you're parked on the suspect commit — not on a branch.

# bisect parks you on the suspect commit
# detached HEAD — don't commit here

$ git bisect reset
# back to where you were before bisect started

reset ends the session. Always run it before doing anything else.
