The index (staging).

What git add parks for the next commit. A holding area between working dir and HEAD.

$ git add app.js
# app.js now lives in the index too

$ git status
Changes to be committed:
  modified:   app.js

Changes not staged for commit:
  modified:   routes/todo.js

Think of it as a draft of your next commit. You decide what goes in.

Stored at .git/index. A literal file. Snapshot-in-progress.

$ # what each verb actually moves

Commands = arrows.

Every git verb is just a move between two trees. That's all.

  • git add <f> working dir → index
  • git commit index → HEAD (new commit)
  • git checkout <f> HEAD → working dir (file restore)
  • git reset <f> HEAD → index (un-stage)
  • git reset --hard HEAD → index + working dir (nuke local)

Learn the trees. The commands name themselves.

$ # debugging "where am I?"

When this clicks, everything clicks.

Three scenarios where the 3-tree model is the whole answer.

"Why didn't my change get committed?"

It wasn't in the index. git add first, then commit.

"Where did my changes go after a reset?"

Depends on --soft / --mixed / --hard. Different combos of trees move.

"How do I undo a stage?"

Move file index → HEAD with git restore --staged <f>.

Every "wait, what happened?" → ask which tree?
