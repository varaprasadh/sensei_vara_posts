$ # what it's for

Rewrote history →
must force.

If you rebased, squashed, or amended, the remote's history no longer matches yours. A normal git push will be rejected.

$ git push
! [rejected]        feature/x -> feature/x (non-fast-forward)
hint: Updates were rejected because the tip of your current
hint: branch is behind its remote counterpart.

Force-push is the override. But there are 2 ways to do it.

$ # what --force actually does

--force = overwrite.

Doesn't check if anyone else pushed since you last pulled. Their commits get nuked.

Teammate's work, deleted. Without warning.

$ # the safety belt

--force-with-lease
= check first.

Only force-push if the remote tip is what you expected. If someone else pushed, the push fails — same as a normal push.

$ git push --force-with-lease
! [rejected]        feature/x -> feature/x (stale info)
# remote moved since you last fetched. NOT overwritten.

# pull / merge / rebase, then try again.

Same use case, no friendly fire.

-f vs --force-with-lease.

Same command. One extra word. Different attitude.

--force

"I don't care what's there.
Use mine."

Can erase teammate's commits. No check, no warning.

--force-with-lease

"Use mine, if remote matches what I last fetched."

Fails safely if someone else pushed. No work lost.

Same command, one extra word, way safer.

$ # the rebase + lease combo

Rebase, then lease.

The everyday flow for cleaning up your feature branch before pushing it back.

$ git fetch                              # know the current state
$ git rebase -i HEAD~5                   # clean up your commits
$ git push --force-with-lease            # safe override

If lease fails: git fetch, decide what to do, retry. Never --force blindly to "unstick" it.

$ # team-friendly habits

When force-push is OK.

A quick map for when to force-push, when to warn, and when to never.

01
Your own feature branch

Fine. Do it freely — with lease.

02
Before PR review starts

Tidy commits, squash fixups — go for it.

03
During PR review

Annoying for reviewers (comments lose anchors). Warn them first.

04
On main / develop / shared trunks

Basically never. You will ruin someone's day.

Set git config --global alias.fpush 'push --force-with-lease' and forget the unsafe version exists.

Quick recap

  • force-push — needed after rebase / squash / amend
  • --force — overwrites, no checks; can nuke teammates' work
  • --force-with-lease — only if remote matches expectation
  • Alias it. Make it your default.
  • Shared trunks (main, develop)? Don't force-push at all.
