Predict next token.
Repeat.

A model generates one token at a time. Each new one depends on everything before it.

prompt → model → "The"
prompt + "The" → model → " capital"
prompt + "The capital" → model → " of"

↻ Until the model emits a stop token, or hits max_tokens.

// the boring way

Without streaming.

You wait for the whole reply. Then render it. Long blank screen, then dump.

const res = await model({
  messages: [...],
  stream: false
});

render(res.text);
// → user stares at spinner for 6 seconds
// → then the whole reply lands at once

Fine for short replies and background jobs. Bad for chat UI.

streaming.js
05 / 08
// the good way

With streaming.

Each token, as it arrives, gets pushed to the UI. Feels instant.

const stream = await model({
  messages: [...],
  stream: true
});

for await (const chunk of stream) {
  appendToUI(chunk.text);
}
// → first token in ~200ms, rest streams in

Same total time. Way better perceived speed.

sse.js
06 / 08
// what's actually on the wire

Server-Sent Events.

The server keeps the HTTP connection open and pushes lines as data is ready.

data: {"delta": "The"}
data: {"delta": " capital"}
data: {"delta": " of"}
data: {"delta": " France"}
data: {"delta": " is"}
data: {"delta": " Paris."}
data: [DONE]

Simpler than WebSockets. One-way. Plain HTTP. Just lines of JSON.

pattern.js
07 / 08
// the dev pattern

Open → on chunk → done.

Three handlers cover almost every streaming UI.

const stream = await model.stream({ messages });

let text = "";

for await (const chunk of stream) {
  if (chunk.type === "delta") {
    text += chunk.text;
    renderPartial(text);             // on chunk
  }
  if (chunk.type === "done") {
    finalize(text);                  // done
  }
}

// + handle disconnect / abort / errors

Add abort handling. Always.
