// what actually happens

Fine-tuning updates weights.

Different from prompting. Different from RAG. Understand the mechanism first.

// fine-tuning
updates weights 
// training loop
for (example of dataset) {
  loss = model.forward(example)
  model.backprop(loss)
  weights.update()  // changed
}
Bakes behaviour into the model. Permanent until retrained.
// RAG / prompting
context injection 
// per call
const ctx = retriever.fetch(query)
model.complete([
  system_prompt,
  ...ctx,       // injected
  user_message  // weights: unchanged
])
Context added at runtime. Weights stay frozen.

FT = change what the model knows how to do. RAG = change what it sees.

When prompting isn't enough.

Two signals. Both must be true before FT is worth exploring.

signal 01
Style won't stick
Model can't follow your specific tone/format consistently — even with 10+ few-shot examples in the prompt.
signal 02
Latency from few-shot
Your few-shot examples make the prompt huge. You're paying extra tokens and adding 200ms+ just to define the format.
check first
Did you try this?
System prompt engineering + 5–10 few-shot examples. Most "style problems" are prompt problems.
check first
Did you try RAG?
If the model lacks domain knowledge (not style), RAG solves it without the training cost.

// when FT makes things worse

When fine-tuning fails you.

Three hard limits. If any apply, stop before you spend the budget.

hard limit 01
Not enough data
Need >1,000 high-quality examples minimum. Under that, you're just overfitting noise.
hard limit 02
Task changes often
FT freezes behaviour. If requirements shift monthly, you're retraining constantly. Prompt changes are free.
hard limit 03
You need reasoning
FT hurts reasoning. It bakes in pattern-matching. For logic / math / multi-step: prompting + CoT beats FT.
// mental model
FT = "compress patterns into weights"
CoT = "reason step by step at inference"

LoRA vs full FT.

LoRA trains small adapters. Full FT updates every weight. Pick based on your constraints.

LoRA / PEFT
// train adapters only
params trained0.1–1% of model
training cost$50–$500
training timehours, not days
qualitygood for style/format
swap-ableyes — hot-swap adapters
base modelunchanged, reusable
Full Fine-tune
// update all weights
params trained100% of model
training cost$500–$5k+
training timedays
qualityhighest (when data good)
swap-ableno — one model per task
base modeloverwritten

Default to LoRA. Full FT only if you have quality data at scale and a dedicated serving setup.

// the ladder, not the jump

The default order.

  • 1
    Prompt engineering
    System prompt + few-shot. Free. Instant. Fixes 80% of "we need to fine-tune" cases.
  • 2
    RAG
    Inject external knowledge at runtime. Fixes domain knowledge gaps without training.
  • 3
    LoRA / PEFT
    Style / format consistency at scale. 1k+ examples needed. Try this before full FT.
  • 4
    Full fine-tune
    Last resort. Needs 5k+ examples, dedicated infra, and clear prompting failure evidence.
Most "we need to fine-tune" decisions are wrong.
Prompt first. Always.
