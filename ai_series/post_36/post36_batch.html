// the concept

What batch APIs are.

Instead of sending requests one at a time, submit thousands at once. Get results back within 24 hours.

// real-time API
synchronous 
request → wait → response
request → wait → response
request → wait → response
// one at a time
// immediate results
// full price
Good for user-facing apps that need instant responses.
// batch API
asynchronous 
[req1, req2, ... req10000]
    ↓ upload
    ↓ processing...
    ↓ poll status
[res1, res2, ... res10000]
// 50% off
Perfect for offline processing where latency doesn't matter.

// why it exists

The economics of waiting.

API providers have GPU idle time. You trade latency for massive discounts.

01 — cost
50% cheaper
Anthropic, OpenAI both offer half-price for batch. On 1M requests, that's thousands saved.
02 — throughput
No rate limits
Batch bypasses per-minute rate limits. Submit 100K requests without throttling.
03 — reliability
Auto-retry built in
Failed requests retry automatically. No 429 errors to handle in your code.
04 — simplicity
Fire and forget
Submit before bed, download results in the morning. No long-running processes to babysit.

The deal: you give up immediacy → provider fills GPU idle time → everyone wins

// the workflow

Four steps to batch.

Upload JSONL, create batch, poll for completion, download results.

step 1
Prepare JSONL
One JSON object per line. Each has a custom_id + your normal API request params.
↓
step 2
Upload & create batch
Upload the file, then POST to /batches with the file ID. Returns a batch_id.
↓
step 3
Poll status
GET /batches/{id} until status = "ended". Typically 1-24 hours depending on size.
↓
step 4
Download results
Fetch the results file. Each line has your custom_id + the model's response.

// practical example

Processing 10K docs.

Classify 10,000 support tickets overnight for $12 instead of $24.

// 1. build the JSONL file
const lines = tickets.map((t, i) => JSON.stringify({
  custom_id: `ticket-${i}`,
  params: {
    model: "claude-sonnet-4-20250514",
    max_tokens: 256,
    messages: [{
      role: "user",
      content: `Classify: ${t.text}`
    }]
  }
}));

// 2. create the batch
const batch = await anthropic.batches.create({
  requests: lines
});

// 3. poll until done
while (batch.status !== "ended") {
  await sleep(60_000);
  batch = await anthropic.batches.retrieve(batch.id);
}

// when to use which

Batch vs real-time.

Not everything should be batched. Here's the decision framework.

// use batch
  • Bulk document classification Thousands of PDFs, emails, or tickets.
  • Dataset enrichment Add summaries, tags, or translations to existing data.
  • Eval & testing Run prompts against test sets. Cheapest way to evaluate.
  • Content generation Generate product descriptions, SEO content at scale.
// use real-time
  • Chat / conversational UI Users expect instant responses.
  • Interactive code assistants Developer tools need sub-second feedback.
  • Real-time moderation Content must be checked before it goes live.
  • Agentic workflows Each step depends on the previous result.

Rule of thumb: no human waiting? → batch it

// production tips

Batch like a pro.

Hard-won lessons from processing millions of batch requests.

// tip 1: always set custom_id
custom_id: `doc-${doc.id}-v${version}`
// → lets you match results back to source

// tip 2: chunk large batches
// 50K requests? split into 5 batches of 10K
// → parallel processing, partial results if one fails

// tip 3: idempotency
// design so re-running the same batch is safe
// → crashed at 60%? just resubmit

// tip 4: use max_tokens wisely
max_tokens: 100  // not 4096!
// → lower max = faster processing + less cost

// tip 5: validate JSONL before upload
// one malformed line = entire batch rejected
