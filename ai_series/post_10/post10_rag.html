// the 5-step recipe

How RAG works.

Once at index time. Four times at query time. Same skeleton everywhere.

1
Embed your docs once — chunks → vectors
2
Store vectors in a vector DB
3
At query time, embed the user's question
4
Retrieve top-k most-similar chunks
5
Stuff chunks into the prompt → grounded answer

// a tiny RAG, in JS

Tiny RAG, in JS.

const qVec = await embed(userQuery);
const docs = await vectorStore.search(qVec, { topK: 3 });

const context = docs.map(d => d.text).join("\n---\n");

const reply = await model({
  messages: [
    { role: "system", content: `Use this context:\n${context}` },
    { role: "user",   content: userQuery }
  ]
});

Real systems add chunking, reranking, citations — same skeleton.

// when to use which

RAG vs fine-tune.

Different tools. Different jobs. Most teams reach for RAG first.

// option A
RAG
  • fresh data, swap anytime
  • cheap — no retraining
  • show citations
  • great for facts & docs
teach it what to know
// option B
fine-tune
  • bakes new behavior in
  • expensive to train
  • frozen at training time
  • great for style & format
teach it how to act

Most teams reach for RAG first. Fine-tune later, if needed.

Quick recap

  • closed-book model — hallucinates on your private/fresh data
  • RAG — retrieve relevant chunks, stuff them in the prompt
  • 5 steps: embed → store → embed query → search → answer
  • Retrieves by meaning via cosine similarity
  • Usually beats fine-tuning for facts & docs
