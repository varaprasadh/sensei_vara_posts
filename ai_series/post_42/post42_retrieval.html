// static RAG

The simple pipeline.

Query comes in, you retrieve once, generate once. No loops. No decisions. Straightforward.

step 1
User query
"What is our refund policy for enterprise customers?"
↓
step 2
Embed & retrieve
Convert query to vector. Find top-k similar chunks from your document store.
↓
step 3
Generate
Send query + retrieved chunks to LLM. Get answer grounded in your docs.
// static RAG in 4 lines
const embedding = await embed(query)
const chunks    = await vectorDB.search(embedding, 5)
const answer    = await llm(query, chunks)  // done

// the breaking point

When RAG breaks.

Some questions need multiple lookups, reasoning between results, or reformulated queries. Static RAG can't do this.

01 — multi-hop
Multi-hop questions
"Which team lead manages the project that uses the most expensive cloud service?" Needs 3 lookups chained together.
02 — ambiguous
Ambiguous queries
"How's our performance?" Performance of what? App latency? Sales? Stock price? Need to clarify then retrieve.
03 — cross-source
Multiple sources
"Compare our pricing to competitor X." Need to search your docs AND competitor data, then synthesize.
04 — bad results
Poor initial retrieval
First query returns irrelevant chunks. A human would rephrase. Static RAG just gives a bad answer.

// agentic retrieval

The agent decides what to retrieve.

Instead of one fixed retrieval, an LLM agent plans searches, evaluates results, and re-queries when needed.

// agentic retrieval loop
async function agenticRAG(query) {
  let context = []
  let plan = await llm("What do I need to look up?", query)

  for (const step of plan.searches) {
    const results = await search(step.query, step.source)

    // evaluate: are these results good enough?
    const eval = await llm("Are these relevant?", results)
    if (!eval.relevant)
      results = await search(eval.betterQuery) // re-query

    context.push(...results)
  }

  return llm(query, context)  // answer with all gathered info
}

// head-to-head

Static RAG vs retrieval agent.

Neither is always better. Choose based on your query complexity and latency budget.

Static RAG Retrieval Agent
Complexity Low — 3 steps, no loops High — planning, eval, retry
Latency ~1-2s (1 retrieval + 1 LLM) ~5-15s (multiple LLM calls)
Cost / query $0.01-0.03 $0.05-0.20
Simple queries Great Overkill
Multi-hop Fails Handles well
Self-correction None Re-queries on bad results

// choosing the right approach

When simple RAG is enough.

Don't over-engineer. Most production RAG use cases work fine with the static pipeline.

// use static RAG
  • FAQ / knowledge base lookup Single doc answers the question
  • Customer support chatbot Answers grounded in help docs
  • Document Q&A "What does section 4.2 say?"
  • Latency-critical apps Need answers in under 2 seconds
// use retrieval agent
  • Research questions Compare data from multiple docs
  • Ambiguous intent Agent clarifies before searching
  • Cross-system queries Search Confluence + Jira + Slack
  • Multi-step reasoning Answer depends on chained lookups

// best of both worlds

The hybrid pattern.

Route simple queries to static RAG. Escalate complex ones to a retrieval agent. Best latency AND accuracy.

// hybrid: classify then route
async function hybridRetrieval(query) {
  // step 1: classify query complexity
  const complexity = await classify(query)
  // "simple" | "multi-hop" | "ambiguous"

  if (complexity === "simple") {
    return staticRAG(query)       // fast path: ~1s
  }

  return agenticRAG(query)        // slow path: ~8s
}

// result:
//   80% of queries → static RAG (fast, cheap)
//   20% of queries → agent (slow but accurate)
//   avg latency stays low, hard questions answered

The classifier is cheap (<100 tokens). It saves you from running an agent on every query.

// recap

Pick the right retrieval.

  • Static RAG: query → retrieve → generate. Simple, fast, cheap. Handles 80% of use cases
  • Retrieval agents plan searches, evaluate results, and re-query when retrieval is poor
  • Use agents for multi-hop questions, ambiguous queries, and cross-source lookups
  • The hybrid pattern: classify query complexity, route simple to RAG, complex to agent
  • Don't over-engineer. Start with static RAG. Add agentic retrieval only when you see failures
