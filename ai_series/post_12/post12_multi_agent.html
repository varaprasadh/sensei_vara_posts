// how they talk

Pass structured payloads.

Agent A's output is agent B's input. Make it a JSON shape, not prose.

// planner → researcher
{
  "from": "planner",
  "to":   "researcher",
  "tasks": [
    { "id": 1, "query": "current weather in Tokyo" },
    { "id": 2, "query": "current weather in Lisbon" }
  ]
}

JSON is contracts. Prose is vibes. Pick contracts.

// who's in charge

Two routing styles.

Same goal, different control flow.

option A

Thin orchestrator

A small coordinator process routes between specialists.

  • Predictable flow
  • Easy to test
  • Plain code, no magic
option B

Agents-as-tools

One agent calls another via the tool interface.

  • Flexible routing
  • Self-directed
  • Harder to trace

Start thin. Grow into agents-as-tools only when you need it.

// when one is enough

Don't split for the sake of it.

Multi-agent isn't a flex. It's a cost.

stay solo

One agent when...

  • Task fits in one prompt
  • Tools < 5
  • Single voice, single goal
  • No clear pipeline shape
split

Multi-agent when...

  • Clear pipeline of stages
  • Parallelizable sub-tasks
  • Conflicting personas
  • Distinct tool sets per role

Multi-agent = more cost, more latency, more places to fail. Earn it.
