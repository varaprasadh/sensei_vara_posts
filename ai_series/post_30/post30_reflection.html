// the reflection loop

Reflection pattern.

Three-step loop. Model generates, critiques, then re-generates with the critique as context.

step 1
Generate
Model produces initial output — code, answer, structured JSON, whatever the task is.
↓
step 2
Self-critique
Same (or second) model receives the output and a critique prompt. Returns a structured list of problems.
↓
step 3
Regenerate
Original prompt + output + critique → new generation. Repeat N times or until no critique.

// when it works

Reflection helps here.

Tasks where correctness is verifiable and errors have clear signatures. The model can find and fix its own mistakes.

01 — code
Code generation
Syntax errors, off-by-one bugs, missing imports — often detectable by model reading its own output.
02 — schema
Structured output
Schema violations are explicit. Critique can name the exact field and rule that failed.
03 — reasoning
Step-by-step logic
Math or multi-step reasoning. Rereading its own chain-of-thought catches sign errors and skipped steps.
04 — format
Output formatting
Missed markdown, wrong columns, bad delimiters — low-level formatting errors the model reliably catches.

Pattern: verifiable constraint → reflection helps

fails.js
04 / 08
// when it backfires

Reflection hurts here.

No external ground truth → model "fixes" output against its own biases. Often loops to worse results.

// breaks down
  • Subjective tasks Model keeps tweaking tone with no clear target — converges to bland.
  • Creative writing Kills voice. Each pass toward "correct" moves further from interesting.
  • High-confidence wrong answers Model confirms its own hallucination. Critique says "looks right."
// the real problem
  • No external signal Without a test, schema, or retrieval check, the critique is just another LLM guess.
  • Sycophantic loop Model critiques → agrees with itself → regenerates same wrong answer more confidently.
  • Cost multiplied 2–3× calls. If reflection doesn't help, you paid extra to get worse output.

Pattern: no verifiable constraint → reflection hurts

// beyond manual reflection

DSPy: prompts as programs.

Don't hand-write critiques. Let a compiler optimize your prompts automatically using labeled examples.

// DSPy: three core ideas

// 1. Signatures — declare intent, not wording
class Summarize(dspy.Signature):
    """Summarize a document into one sentence."""
    doc    = dspy.InputField()
    summary = dspy.OutputField()

// 2. Modules — compose pipelines
summarizer = dspy.ChainOfThought(Summarize)

// 3. Compile — optimizer rewrites prompts
compiled = BootstrapFewShot(metric=rouge_score)
optimized_prog = compiled.compile(summarizer, trainset=examples)

Prompts become parameters. Metric drives improvement. No manual critique loop needed.

// the rule that actually works

Reflect on failures only.

Don't always reflect. Generate → verify against external ground truth → reflect only when verification fails.

// pattern that works
for attempt in range(3):
    output = generate(prompt)

    // verify against EXTERNAL ground truth
    result = verify(output)   // run tests, check schema,
                               // query DB, call API
    if result.ok:
            return output           // done — no reflection needed

    // only reflect on ACTUAL failures
    prompt = add_critique(prompt, result.errors)
raise MaxAttemptsExceeded()  // escalate, don't loop forever

Key: the verifier is external. Not the model judging itself.
